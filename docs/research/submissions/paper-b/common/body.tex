\begin{abstract}
Autonomous agents increasingly act on a user's behalf carrying OAuth/MCP bearer
tokens, yet the authorization layer around them is new and largely unsystematized.
We survey and organize the authorization threat model for agent and Model Context
Protocol (MCP) deployments into six categories---audience binding, delegation,
scope, agent identity, confused-deputy, and agency---and map each of 15 threats to
its normative source (OAuth RFCs 8693/8707/9728/9700, the MCP authorization
specification, OWASP LLM \& Agentic Top~10s, CWEs) and to a concrete invariant that
must hold. We show which threats are decidable from a single token or server
manifest (6 of 15 are statically checkable, and we provide an open-source analyzer
for them) and which fundamentally require runtime consent, human-in-the-loop, or
workload identity. \gate{a measurement of prevalence across public MCP
deployments; this submission is positioned as SoK / work-in-progress and the
empirical section is a gate.}
\end{abstract}

\section{Introduction}
When an agent calls a tool or an MCP server on a user's behalf, a bearer token
travels with the request. The failure modes are OAuth failure modes with sharper
consequences because the caller is autonomous and can be steered by untrusted
input: a token not bound to the resource it is presented to can be replayed or
passed through (a confused deputy); an on-behalf-of token with no verifiable
delegation chain makes ``who authorised this?'' unanswerable; an omnibus scope
(\texttt{admin:*}) hands an injected agent the keys to everything; and a
non-expiring credential never stops being useful. These map onto the MCP
authorization specification~\cite{mcpauth}, OAuth token exchange~\cite{rfc8693},
and the OWASP LLM/Agentic Top~10s~\cite{owaspllm,owaspagentic}---but no systematic,
source-grounded treatment ties them together. This SoK does so, and separates what
is statically checkable from what is not.

For each threat the invariant is precise. \emph{Audience binding:} a token MUST
carry a resource indicator naming the server it is presented to, or it is
replayable/passthrough-able~\cite{rfc8707,rfc9728,mcpauth}. \emph{Delegation:} an
on-behalf-of token MUST carry a verifiable \texttt{act} chain, and token exchange
MUST honour \texttt{may\_act} so only pre-authorized actors obtain a delegated
token~\cite{rfc8693}. \emph{Scope:} agents MUST hold least-privilege, expiring
credentials distinct from the user's~\cite{owaspllm,mcpauth}. \emph{Identity:}
sessions MUST NOT serve as authentication, and each agent MUST have a verifiable
identity distinct from the human~\cite{mcpauth,wimse,spiffe}. \emph{Confused
deputy:} an OAuth proxy MUST obtain per-client user consent and enforce exact
\texttt{redirect\_uri} matching~\cite{mcpauth,rfc7591,cwe441}. \emph{Agency:}
high-impact actions MUST require per-action authorization or a human in the loop so
that prompt injection cannot escalate~\cite{owaspllm,owaspagentic}.

\section{What is statically decidable, and what is not}\label{sec:gap}
A central observation: \textbf{6 of 15 threats (audience binding, \texttt{act}
delegation, scope, expiry) are decidable from a single token or manifest}; the
remaining 9 are not, because they depend on runtime consent flows (CD-01/02),
server-side enforcement and human-in-the-loop (AGT-01/02, DEL-03/04, SCOPE-03), or
a workload-identity substrate the ecosystem is still standardizing (AID-01/02).
This line matters for tooling and for the ecosystem: classic OAuth machinery
(resource indicators, token exchange, protected-resource metadata) \emph{models}
several of these, but common MCP deployments rarely \emph{verify} them, leaving the
non-static threats to the deployer---exactly where they are most often missed.

\section{An instrument for the statically-checkable subset}\label{sec:instrument}
We provide an open-source static analyzer that decodes a token and emits cited
findings against a policy: audience binding (MCP-01/02), on-behalf-of delegation
(DEL-01/02), scope minimisation (SCOPE-01), and expiry (SCOPE-02). It is stateless
and runs on a single token---in CI or client-side---so nothing leaves the caller.
It thus covers the 6 statically-decidable threats of \S\ref{sec:gap}; the taxonomy
names the remaining 9 as out of static scope.

\section{Related work}\label{sec:related}
Our building blocks are the OAuth 2.0 framework~\cite{rfc6749} and its security
BCP~\cite{rfc9700}, token exchange~\cite{rfc8693}, resource
indicators~\cite{rfc8707}, protected-resource metadata~\cite{rfc9728}, and dynamic
client registration~\cite{rfc7591}; JWT best practices~\cite{rfc8725}; and the MCP
authorization specification~\cite{mcpauth}. The confused-deputy problem is
classical~\cite{hardy1988confused,cwe441}. Emerging drafts address on-behalf-of
agent authentication~\cite{oboagents} and workload
identity~\cite{wimse,spiffe}. Practitioner taxonomies exist
(OWASP~\cite{owaspllm,owaspagentic}), but a source-grounded systematization that
maps each threat to a checkable invariant and to what is statically decidable---and
an accompanying open analyzer---is, to our knowledge, novel; establishing that gap
precisely is part of this SoK.

\section{Threats to validity}
The MCP specification is fast-moving; the systematization is date-stamped and its
coverage is a snapshot that will need revision as the standard evolves. The
static/runtime decidability line depends on token/manifest availability; a
deployment that hides relevant state reduces what any static tool can conclude. Any
future measurement will skew toward early-adopter public MCP servers, which we will
report rather than hide.

\section*{Ethics considerations}
The systematization uses only public specifications, advisories, and CVEs. The
accompanying analyzer runs on tokens the operator already holds and sends nothing
anywhere. We probe no third-party live agents or MCP servers and use no real user
tokens. Any future measurement will characterise population prevalence, not single
deployments, and will follow coordinated responsible disclosure for identifiable
high-severity findings. No personal data or human subjects are involved.

\section*{Open science}
We release the static analyzer and the machine-readable threat taxonomy (each
threat with its invariant and normative sources) under an open licence so the
systematization is inspectable and the checkable subset is reproducible.

\section{Conclusion}
Agent authorization is an under-studied, high-stakes surface. We contribute a
source-grounded systematization of 15 threats and their invariants, a precise
static-vs-runtime decidability line, and an open-source instrument for the
statically-checkable subset, as the foundation for a forthcoming measurement.
